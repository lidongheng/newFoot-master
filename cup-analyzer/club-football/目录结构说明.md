# club-football 目录结构说明

## 1. 这个目录解决什么问题

`club-football` 是俱乐部足球的对象域，核心原则是：

- 一支球队只有一个球队对象；
- 球队参加多项赛事时，不复制球队对象；
- 一场比赛只有一份中立事实；
- 基本面、盘口、热度和理论方法的分析结果按球队视角保存。

例如阿森纳同时参加英超、欧冠、足总杯和英联杯，项目中仍然只有：

```text
teams/arsenal/
```

四项赛事只是阿森纳在对应赛季中的四条参赛关系，记录在 `competitions/memberships.json`。

## 2. 总体目录结构

下面同时展示当前已有目录和运行工作流后按需生成的目录。标注“按需生成”的文件，在尚未运行对应命令时不会出现。

```text
club-football/
├── README.md
├── 目录结构说明.md
├── 标准基本面工作流.md
├── teams/
│   └── <team-slug>/
│       ├── team.json
│       └── seasons/                         # 深度球队才会建立
│           └── <season>/
│               ├── README.md
│               ├── competitions/
│               │   └── memberships.json
│               ├── fundamentals/
│               │   ├── squad/
│               │   │   └── draft.md
│               │   ├── squad-final/
│               │   │   └── confirmed.md
│               │   ├── team-profile.md                    # 按需生成
│               │   └── history-match-profile.md           # 按需生成
│               └── matches/                               # 按需生成
│                   └── <matchId>/
│                       ├── market-analysis.json
│                       ├── heat-analysis.json
│                       └── methods/                        # 理论方法结果
└── matches/                                                # 按需生成
    └── <matchId>/
        ├── match.json
        └── facts/
            ├── market-snapshots.jsonl
            └── heat-signals.json
```

## 3. 根目录文件

### `README.md`

简要说明 `club-football` 的职责，以及球队对象和比赛对象的基本边界。

### `目录结构说明.md`

就是本文档。用于解释每个子目录和文件的用途、生成方式和维护责任。

### `标准基本面工作流.md`

记录可实际执行的命令，包括：

1. 生成大名单草稿；
2. 初始化人工确认名单；
3. 人工确认门禁；
4. 生成球队画像；
5. 生成历史比赛画像；
6. 创建比赛对象；
7. 抓取盘口快照；
8. 执行盘口和热度分析。

## 4. `teams`：球队对象目录

### 4.1 `<team-slug>` 是什么

每支俱乐部拥有一个稳定英文 slug，例如：

```text
teams/arsenal/
teams/fc-seoul/
teams/manchester-city/
teams/pohang-steelers/
```

slug 用于项目内部路径，不随中文名称、简称或参赛赛事变化。

同一支球队出现在其他赛事时，必须继续使用原来的球队目录，不能在赛事目录或 `teams` 下再复制一份。

### 4.2 `team.json`

`team.json` 保存球队稳定身份，例如：

- 对象类型；
- 中文名和英文名；
- Titan007 球队 ID；
- 当前分析级别；
- 深度球队的活动赛季。

球队有两种分析级别：

| `analysisLevel` | 含义 |
| --- | --- |
| `identity` | 最小身份对象，目前只登记“这支球队是谁” |
| `deep` | 深度分析对象，拥有赛季、基本面、比赛视角分析等内容 |

当前阿森纳和 FC 首尔是 `deep`，其他英超、韩 K 参赛队先是 `identity`。需要深入分析某支球队时，再把它晋升为深度对象，而不是提前生成大量空画像。

`team.json` 属于球队身份数据。确认球队映射无误后，不应由比赛分析过程反复改写。

## 5. `seasons`：球队的赛季状态

```text
teams/<team-slug>/seasons/<season>/
```

赛季目录保存球队在特定赛季中的可变状态。球队身份长期存在，但大名单、参赛赛事、比赛和分析结论会随赛季变化，所以不能直接全部堆在球队根目录。

赛季名称示例：

```text
arsenal/seasons/2026-2027/
fc-seoul/seasons/2026/
```

- 跨年赛季使用 `2026-2027`；
- 自然年赛季使用 `2026`。

### `README.md`

说明这支球队在该赛季的用途和工作流状态。它是给人阅读的操作说明，不是分析器输入。

## 6. `competitions`：参赛关系

### `memberships.json`

记录球队在该赛季参加哪些赛事。

阿森纳示例：

```json
{
  "teamId": 19,
  "season": "2026-2027",
  "competitions": [
    "premier-league",
    "uefa-champions-league",
    "fa-cup",
    "efl-cup"
  ]
}
```

这里表达的是“阿森纳参加了四项赛事”，不是保存四份阿森纳数据。

赛事规则、积分榜和轮次仍属于赛事上下文，不应该写进 `team.json`。

## 7. `fundamentals`：基本面标准工作流

```text
fundamentals/
├── squad/draft.md
├── squad-final/confirmed.md
├── team-profile.md
└── history-match-profile.md
```

这四个文件存在严格的先后关系。

### 7.1 `squad/draft.md`

大名单草稿，由程序根据抓取和俱乐部比赛分析结果生成。

- 可以重新生成；
- 不是最终名单；
- 不能直接作为正式球队画像的输入；
- 允许包含需要人工补充的信息。

### 7.2 `squad-final/confirmed.md`

人工确认后的最终大名单，是基本面分析的强制门禁。

初始化时文件首行为：

```text
<!-- confirmation-status: pending -->
```

人工核对名单、伤停、伤疑、主教练和阵型后，手动改成：

```text
<!-- confirmation-status: confirmed -->
```

维护规则：

- 程序只负责从草稿初始化一次；
- 文件已存在时，初始化器拒绝覆盖；
- 人工修改和确认后，不允许爬虫自动重写；
- 状态不是 `confirmed` 时，球队画像和历史比赛画像都必须停止；
- 正式流程不会静默回退到原始球员 JSON。

### 7.3 `team-profile.md`

球队画像，由 `confirmed.md` 生成，包含球队阵容结构、位置配置、阵型和其他基本面信息。

- 由程序生成；
- 输入必须是已人工确认的大名单；
- 文件不存在通常表示尚未通过人工确认，或者尚未运行画像命令。

### 7.4 `history-match-profile.md`

球队历史比赛画像，将已确认名单与历史比赛阵容、首发和比赛表现关联起来。

- 由程序生成；
- 输入必须是已人工确认的大名单；
- 服务于跨赛事、跨比赛的球队长期分析；
- 不属于某一个联赛，因此保存在球队目录中。

## 8. 两种 `matches` 为什么同时存在

项目中有两种比赛目录，但职责完全不同。

```text
club-football/matches/<matchId>/
club-football/teams/<slug>/seasons/<season>/matches/<matchId>/
```

### 8.1 根级 `matches/<matchId>`：中立比赛事实

这里只保存双方共享的一份事实，不站在任何球队立场。

#### `match.json`

比赛身份文件，记录：

- 比赛 ID；
- 所属赛事；
- 开球时间；
- 主队 ID；
- 客队 ID。

创建后拒绝覆盖。如果比赛信息确实有误，应先人工确认原因，再进行针对性修改。

#### `facts/market-snapshots.jsonl`

原始盘口时间序列。每一行都是一个独立 JSON 快照。

支持的检查点：

- `opening`：初盘阶段；
- `analysis`：常规分析阶段；
- `lineup`：首发公布阶段；
- `closing`：临场阶段。

该文件只允许追加，不允许用最新数据覆盖旧数据。这样才能分析盘口在不同时间点如何变化。

亚盘统一保存为主队视角：

- 主队让球为负数；
- 主队受让为正数。

#### `facts/heat-signals.json`

保存有来源的热度信号。热度必须区分：

- `observed`：直接观测到的数据或事实；
- `inferred`：基于已记录事实做出的推断。

观测信号必须记录来源和抓取时间，推断信号必须记录推断依据。没有真实投注比例时，不允许填写 50% 或其他中性兜底值。

### 8.2 球队赛季下的 `matches/<matchId>`：球队视角分析

这里不再保存比赛原始事实，而是保存某支球队如何看待该场比赛。

例如一场阿森纳对利物浦的比赛：

```text
club-football/matches/123456/match.json
club-football/teams/arsenal/seasons/2026-2027/matches/123456/
club-football/teams/liverpool/seasons/2026-2027/matches/123456/
```

根级比赛事实只有一份；阿森纳视角和利物浦视角的分析可以各有一份。

#### `market-analysis.json`

球队视角的盘口分析结果，包括：

- 当前球队是主队还是客队；
- 对手是谁；
- 已抓取哪些盘口检查点；
- 不同公司的盘口、水位是否发生变化；
- 原始盘口采用什么视角和符号规则。

它是派生结果，可以根据新增盘口快照重新生成。

#### `heat-analysis.json`

球队视角的热度分析结果。

- 有合格热度信号时，状态为 `analyzed`；
- 缺少 `heat-signals.json` 时，状态为 `blocked`；
- `blocked` 文件会明确列出缺失输入，不生成伪造数据。

#### `methods/`

保存未来理论方法对该场比赛、该支球队的执行结果。

例如未来实现“安全边际”或“周期定位”后，结果应写在球队比赛视角下，而方法实现本身仍放在项目根目录的 `methodology` 中。

## 9. 文件维护责任

| 文件 | 生成者 | 是否人工编辑 | 是否允许覆盖 |
| --- | --- | --- | --- |
| `team.json` | 球队对象初始化器 | 映射错误时可人工修正 | 已存在时不自动覆盖 |
| `memberships.json` | 当前为初始化配置 | 可以 | 需要明确更新赛季关系 |
| `squad/draft.md` | 大名单处理器 | 可以补充，但可被重新生成 | 允许重新生成 |
| `squad-final/confirmed.md` | 初始化器创建，人工确认 | 必须人工确认 | 禁止自动覆盖 |
| `team-profile.md` | 球队画像生成器 | 原则上不直接维护 | 允许从确认名单重建 |
| `history-match-profile.md` | 历史比赛画像生成器 | 原则上不直接维护 | 允许从确认名单和比赛数据重建 |
| `match.json` | 比赛对象初始化器 | 确认错误后才修改 | 创建器拒绝覆盖 |
| `market-snapshots.jsonl` | 盘口快照爬虫 | 不应手工改历史行 | 只追加，不覆盖 |
| `heat-signals.json` | 数据采集或人工整理 | 可以，但必须保留来源 | 按事实维护 |
| `market-analysis.json` | 盘口分析器 | 不建议直接修改 | 允许重建 |
| `heat-analysis.json` | 热度分析器 | 不建议直接修改 | 允许重建 |
| `methods/*` | 理论方法执行器 | 不建议直接修改 | 允许重建 |

## 10. 当前实际状态

当前 `club-football` 中：

- 英超和韩 K 参赛队已经拥有最小 `team.json`；
- 阿森纳和 FC 首尔是深度球队对象；
- 阿森纳已建立 2026-2027 赛季和四项参赛关系；
- FC 首尔已建立 2026 赛季、韩 K 参赛关系、大名单草稿和待人工确认名单；
- FC 首尔的 `confirmed.md` 仍是 `pending`，所以球队画像和历史比赛画像尚未生成；
- 根级 `matches` 以及球队赛季下的比赛分析目录，会在首次创建比赛对象和运行分析后按需出现。

## 11. 与旧赛事目录的关系

`epl`、`koreanKLeague`、`championsLeague` 等旧目录当前仍然存在，处于兼容迁移阶段。

- 世界杯现有工作流和数据保持不变；
- 旧俱乐部画像不会自动进入新球队记忆；
- 深度球队的新基本面产物写入 `club-football/teams`；
- 赛事规则、赛程和尚未迁移的数据暂时继续保存在旧赛事目录；
- 确认新结构稳定后，再逐赛事迁移和归档旧资料。

不能因为旧赛事目录中已有一份球队画像，就把它复制到多个新目录中。迁移时应先判断内容的主语：球队内容归球队，比赛事实归比赛，赛事规则归赛事。
